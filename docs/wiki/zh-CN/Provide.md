# Provide - 提供机制

## 说明

提供机制是 Judge 中用于统一获取外部数据的查询链路。

在一次评价任务中，分析器通常需要读取历史数据、实时数据、辅助时间范围或其它外部系统中的业务数据。
如果分析器直接对接每一种数据源，分析逻辑就会与数据访问逻辑耦合，后续切换数据源、调整查询参数或复用分析器都会变得困难。

提供机制将数据访问过程封装为统一的查询入口。 调用方只需要提交查询信息，系统根据配置完成查询前适配、数据提供和查询后过滤，最后返回统一结构的查询结果。

本文只介绍提供机制的整体设计和运行流程。提供器、适配器、过滤器以及预置实现将在独立文档中说明。

## 设计理由

Judge 面向的是可配置的数据评价链路。不同业务场景中，分析器需要的数据可能来自数据库、时序库、消息系统、脚本计算结果或内部辅助数据。
这些数据源的连接方式、参数格式和返回结构往往不同，但分析器真正关心的是能否获得可用于分析的数据。

提供机制的目标是把“数据从哪里来”“查询参数如何表达”“结果如何整理”从分析器中拆出。 这样，分析器可以通过统一的 `lookup`
入口获取数据，而数据访问差异由提供机制处理。

提供机制主要解决以下问题：

1. 统一查询入口，降低分析器与外部数据源的耦合。
2. 支持同类型多实例配置，使同一种查询能力可以使用不同参数服务不同场景。
3. 支持查询前适配与查询后过滤，避免调用方承担数据源差异。
4. 复用外部连接、客户端或脚本状态，降低频繁初始化资源的成本。
5. 通过支持信息向管理界面和运维侧暴露当前系统可用的类型。

## 查询链路

提供机制以 `LookupInfo` 描述查询请求，以 `LookupResult` 返回查询结果。

一次典型查询链路如下：

```text
LookupInfo
  -> Adapter
  -> ProviderSession
  -> Filter
  -> LookupResult
```

`Adapter` 和 `Filter` 是可选环节。 未配置适配器时，原始查询预设和查询参数会直接传给提供器；未配置过滤器时，提供器返回的数据和元数据会直接作为最终结果返回。

`ProviderSession` 是实际执行查询的会话对象。它由提供器创建，并由系统持有和复用。

## 查询信息与查询结果

`LookupInfo` 是一次查询的输入信息，核心字段如下：

| 字段名            | 类型        | 说明                                             |
|-------------------|-------------|--------------------------------------------------|
| `providerInfoKey` | `LongIdKey` | 提供器信息主键，用于指定实际查询数据的提供器。   |
| `adapterInfoKey`  | `LongIdKey` | 适配器信息主键，可以为空。                       |
| `filterInfoKey`   | `LongIdKey` | 过滤器信息主键，可以为空。                       |
| `preset`          | `String`    | 查询预设，用于区分同一提供器支持的不同查询方式。 |
| `objs`            | `Object[]`  | 查询参数数组，用于传递预设需要的参数。           |

`LookupResult` 是一次查询的输出信息，核心字段如下：

| 字段名  | 类型                        | 说明                                                       |
|---------|-----------------------------|------------------------------------------------------------|
| `datas` | `List<Map<String, Object>>` | 数据列表，每个元素表示一条数据记录。                       |
| `meta`  | `Map<String, Object>`       | 元数据，用于描述数据列表或补充分页、统计、时间范围等信息。 |

`objs`、`datas`、`meta` 中的值应尽量使用字符串、数字、布尔值、时间戳等简单对象。 不建议在这些结构中传递数据库连接、文件句柄、网络连接等复杂运行资源。

## 提供信息

提供机制由三类信息实体描述运行实例：

| 实体           | 说明                 |
|----------------|----------------------|
| `ProviderInfo` | 描述一个提供器实例。 |
| `AdapterInfo`  | 描述一个适配器实例。 |
| `FilterInfo`   | 描述一个过滤器实例。 |

三类信息实体具有一致的基础字段：

| 字段名    | 类型        | 说明                                 |
|-----------|-------------|--------------------------------------|
| `key`     | `LongIdKey` | 信息主键。                           |
| `enabled` | `boolean`   | 是否启用。                           |
| `type`    | `String`    | 类型，用于匹配对应的制造器或注册器。 |
| `param`   | `String`    | 参数，具体格式由对应类型决定。       |
| `remark`  | `String`    | 备注。                               |

同一种 `type` 可以对应多条不同的信息实体。 因此，同一种提供器、适配器或过滤器类型可以使用多套参数，服务不同查询场景。

## 支持信息

提供机制通过支持信息描述当前系统支持哪些类型。

| 实体              | 说明             |
|-------------------|------------------|
| `ProviderSupport` | 描述提供器类型。 |
| `AdapterSupport`  | 描述适配器类型。 |
| `FilterSupport`   | 描述过滤器类型。 |

支持信息包含类型标识、显示标签、说明和示例参数，主要用于管理界面、运维命令和配置人员参考。

支持信息只描述“系统支持什么类型”，信息实体则描述“当前启用了哪些实例”。 二者分离后，同一种类型可以创建多个实例，每个实例使用独立参数。

## 接口

提供机制涉及的核心接口如下：

| 接口              | 说明                                               |
|-------------------|----------------------------------------------------|
| `Adapter`         | 查询前适配接口，用于转换 `preset` 和 `objs`。      |
| `Provider`        | 提供器入口接口，用于创建 `ProviderSession`。       |
| `ProviderSession` | 提供器会话接口，用于打开会话、执行查询和关闭会话。 |
| `Filter`          | 查询后过滤接口，用于处理 `datas` 和 `meta`。       |
| `ProvideHandler`  | 提供机制门面接口，对内部调用方暴露统一查询方法。   |

具体方法、参数格式和二次开发要求请参阅对应接口的 JavaDoc 或后续专题文档。

## 提供机制的生命周期

### 构造

当系统需要使用某个提供、适配或过滤实例时，会根据对应信息实体的主键从本地缓存中获取实例。 如果缓存不存在，系统会读取信息实体，并使用其中的
`type` 和 `param` 构造实例。

构造时，系统会在当前容器中寻找支持指定 `type` 的制造器或注册器。 如果没有实现支持该类型，则会抛出类型不支持异常。

### 建立会话

提供器不直接执行查询，而是通过 `newSession()` 创建提供器会话。

首次查询某个提供器信息对应的数据时，系统会创建 `ProviderSession`，并调用 `openSession()`。
会话建立阶段通常用于准备外部连接、客户端、脚本状态或其它长期资源。

建立成功后，会话会被持有，后续查询复用同一个会话。

### 执行查询

执行查询时，系统先展开 `LookupInfo`。

如果查询指定了适配器，则先调用适配器转换 `preset` 和 `objs`。 随后系统获取提供器会话，并调用会话的查询方法获得 `datas` 和
`meta`。

如果查询指定了过滤器，则继续调用过滤器处理查询结果。 最后系统将处理后的 `datas` 和 `meta` 包装为 `LookupResult` 返回给调用方。

### 关闭会话

查询结束不等同于会话关闭。提供器会话通常会被继续持有，以便后续查询复用。

当系统执行提供功能重置、会话清理或程序关闭时，会对当前持有的提供器会话调用 `closeSession()`，随后清空会话映射。

提供器会话实现应能安全处理关闭过程中的资源释放，例如外部连接关闭、客户端停止和临时缓存清理。

## 工作机制

提供机制的核心是“配置化查询流水线”。

调用方通过统一入口提交 `LookupInfo`，运行期根据其中的信息主键装配查询链路。

适配器用于解决查询参数差异。调用方可以使用统一业务参数，由适配器转换成目标提供器能识别的预设和参数数组。

提供器用于解决数据来源差异。不同提供器可以访问不同外部系统，也可以生成内部辅助数据，但对调用方统一返回 `datas` 和 `meta`。

过滤器用于解决结果形态差异。它可以裁剪字段、重命名字段、过滤数据、补充元数据或做其它轻量后处理。

本地缓存用于避免重复构造实例。会话持有机制用于复用外部资源，降低频繁初始化连接、客户端或脚本状态的成本。

## 运维与配置

启用提供机制相关扩展时，需要在可选配置文件中加载对应组件：

| 配置文件               | 说明             |
|------------------------|------------------|
| `opt/opt-provider.xml` | 加载提供器扩展。 |
| `opt/opt-adapter.xml`  | 加载适配器扩展。 |
| `opt/opt-filter.xml`   | 加载过滤器扩展。 |

新增或调整扩展类型后，可以通过支持信息重置命令刷新支持实体。

修改信息实体参数后，运行中的实例或会话可能仍持有旧配置。 此时应根据需要清理本地缓存或重置提供功能，使新配置重新生效。

可通过 Telqos 的提供器会话命令查看和清理当前持有的提供器会话。
