# Analyser - 分析器

## 说明

分析器用于在 Judge 的任务执行过程中处理数据，并生成分析结果或中间结果。

一次评价任务通常需要读取外部数据、已有分析结果或分析器自身保存的状态，再执行统计、转换、聚合、特征提取等逻辑。
如果这些逻辑直接写入作业处理器，任务调度、数据访问和业务分析会相互耦合，不利于扩展和维护。

分析器将具体的数据分析过程封装为统一的执行器接口。 
每个分析器通过 `AnalyserInfo` 配置类型和参数，系统按照分析器信息的顺序创建并执行分析器执行器。

分析器是任务执行链路中的第一个处理阶段，典型链路如下：

```text
创建任务
  -> 分析
  -> 判断
  -> 可视化
  -> 下沉
  -> 完成任务
```

分析器通过 `Context` 读取分析器变量和已有分析结果，也可以调用 [Provide](./Provide.md) 查询外部数据，
并将处理结果保存为当前任务的 `Analysis`。

本文介绍分析器本身的信息实体、接口、生命周期和运行机制；
项目内置的具体实现请参阅 [Preset Analyser Implements](./PresetAnalyserImplements.md)。

## AnalyserInfo

`AnalyserInfo` 描述部件中的一个分析器运行实例，关键字段如下：

| 字段         | 类型        | 说明                                                         |
|--------------|-------------|--------------------------------------------------------------|
| `key`        | `LongIdKey` | 分析器信息主键。                                             |
| `sectionKey` | `LongIdKey` | 分析器所属的部件主键。                                       |
| `index`      | `int`       | 分析器在所属部件中的执行顺序，数值较小的分析器优先执行。     |
| `enabled`    | `boolean`   | 是否启用；只有启用的分析器信息会进入作业本地缓存和执行链路。 |
| `type`       | `String`    | 分析器类型标识，用于匹配对应的 `AnalyserMaker`。             |
| `param`      | `String`    | 分析器构造参数，具体格式由分析器类型决定。                   |
| `remark`     | `String`    | 备注。                                                       |

一个部件可以配置多个 `AnalyserInfo`。 系统读取指定部件下全部启用的分析器信息，并按照 `index` 升序构造执行链。

同一种 `type` 可以对应多条 `AnalyserInfo`。
因此，同一种分析器实现可以使用不同参数构造多个运行实例，并在同一个部件中承担不同的数据处理步骤。

分析器按 `AnalyserInfo.key` 进入作业本地缓存中的信息映射和实例映射。
当分析器信息未启用时，系统不会为其构造分析器，也不会在任务中执行该分析器。

如果 `type` 没有对应的制造器，系统抛出不支持分析器类型异常。
如果 `param` 无法被对应实现解析，系统在构造分析器时抛出分析器制造异常。

## AnalyserVariable

`AnalyserVariable` 用于保存分析器自身需要跨任务维护的状态。

分析器变量的主键由分析器信息主键和变量字符串标识组成：

| 字段                 | 类型     | 说明                             |
|----------------------|----------|----------------------------------|
| `analyserInfoLongId` | `Long`   | 变量所属的分析器信息主键。       |
| `variableStringId`   | `String` | 分析器内部约定的变量字符串标识。 |

变量实体的关键字段如下：

| 字段           | 类型                  | 说明                 |
|----------------|-----------------------|----------------------|
| `key`          | `AnalyserVariableKey` | 分析器变量复合主键。 |
| `valueType`    | `int`                 | 变量值类型。         |
| `stringValue`  | `String`              | 字符串值。           |
| `longValue`    | `Long`                | 长整型值。           |
| `doubleValue`  | `Double`              | 双精度浮点值。       |
| `booleanValue` | `Boolean`             | 布尔值。             |
| `dateValue`    | `Date`                | 日期值。             |

变量值类型与有效值字段的对应关系如下：

| 类型常量                      | 枚举值 | 有效字段       |
|-------------------------------|--------|----------------|
| `VARIABLE_VALUE_TYPE_STRING`  | `0`    | `stringValue`  |
| `VARIABLE_VALUE_TYPE_LONG`    | `1`    | `longValue`    |
| `VARIABLE_VALUE_TYPE_DOUBLE`  | `2`    | `doubleValue`  |
| `VARIABLE_VALUE_TYPE_BOOLEAN` | `3`    | `booleanValue` |
| `VARIABLE_VALUE_TYPE_DATE`    | `4`    | `dateValue`    |

分析器变量归属于 `AnalyserInfo`，不归属于某一次任务。
同一个分析器实例在不同任务中可以通过相同的 `variableStringId` 读取和更新同一份状态。

变量适合保存游标、上次处理时间、累计计数、动态阈值或其它需要跨任务延续的小型状态。
任务本次执行产生的业务结果应保存为 `Analysis`，不应使用分析器变量代替任务分析结果。

## AnalyserSupport

`AnalyserSupport` 描述当前节点支持的一种分析器类型，关键字段如下：

| 字段           | 类型          | 说明                                          |
|----------------|---------------|-----------------------------------------------|
| `key`          | `StringIdKey` | 分析器类型标识，与 `AnalyserInfo.type` 对应。 |
| `label`        | `String`      | 分析器类型的显示名称。                        |
| `description`  | `String`      | 分析器类型的说明。                            |
| `exampleParam` | `String`      | 示例构造参数。                                |

分析器注册通常同时实现 `AnalyserMaker` 和 `AnalyserSupporter`。
`AnalyserMaker` 负责根据类型和参数构造分析器，`AnalyserSupporter` 负责提供类型、标签、说明和示例参数。

系统启动或执行支持重置时，会收集 Spring 容器中的 `AnalyserSupporter` 并更新 `AnalyserSupport`。
管理端可以读取这些信息，展示当前部署实际加载的分析器类型及其示例参数。

`AnalyserSupport` 只描述类型支持能力，不代表已经存在对应的 `AnalyserInfo`，
也不代表某个部件的作业本地缓存中已经构造了该类型的分析器。

## 接口

### Analyser

分析器 `Analyser` 是创建分析器执行器的入口，主要方法如下：

| 方法签名                                          | 说明                       |
|---------------------------------------------------|----------------------------|
| `Executor newExecutor() throws AnalyserException` | 创建一个新的分析器执行器。 |

具体实现通常继承 SDK 中的 `AbstractAnalyser`，并实现创建执行器的模板方法。
分析器可以保存构造参数、已编译脚本、转换规则或创建执行器所需的其它只读状态。

分析器实例会进入作业本地缓存，并被同一部件的多个任务复用。
具体实现如果在分析器实例中保存可变状态，需要自行考虑并发任务访问时的线程安全问题。

### Executor

`Analyser.Executor` 表示一次任务中执行一个分析器的执行器，主要方法如下：

| 方法签名                          | 说明                       |
|-----------------------------------|----------------------------|
| `void init(Context context)`      | 初始化执行器并设置上下文。 |
| `void analyse() throws Exception` | 执行分析逻辑。             |

具体实现通常继承 SDK 中的 `AbstractExecutor`。
抽象实现保存 `Context`，具体执行器在 `analyse()` 中使用该上下文读取数据和持久化结果。

系统每次执行任务时都会为每个分析器创建新的执行器。
执行器只服务于当前任务，不会进入作业本地缓存，也不会在不同任务之间复用。

`Executor` 没有显式的关闭或销毁方法。
如果执行器在 `analyse()` 中临时打开流、连接或其它资源，应在方法内部使用可靠的清理机制及时释放。

### Context

`Analyser.Context` 表示分析器执行时可访问的任务上下文。
上下文由系统创建，并绑定当前部件、分析器信息和任务。

上下文提供的主要能力如下：

| 能力           | 相关方法                                                                                     | 说明                                            |
|----------------|----------------------------------------------------------------------------------------------|-------------------------------------------------|
| 获取当前对象   | `getSectionKey()`、`getAnalyserInfoKey()`、`getTaskKey()`                                    | 获取当前部件、分析器信息和任务主键。            |
| 更新任务信息   | `updateTaskModal(...)`、`createTaskEvent(...)`                                               | 更新任务锚点消息并记录任务事件。                |
| 维护分析器变量 | `inspectAnalyserVariable(...)`、`upsertAnalyserVariable(...)`、`removeAnalyserVariable(...)` | 读取、写入和删除分析器自身状态。                |
| 维护分析结果   | `inspectAnalysis(...)`、`upsertAnalysis(...)`、`removeAnalysis(...)`                         | 读取、写入和删除当前任务的分析结果。            |
| 下载图片结果   | `downloadPictureFile(...)` 等方法                                                            | 下载分析图片、图片流、缩略图及图片包条目。      |
| 下载文件结果   | `downloadFileFile(...)` 等方法                                                               | 下载分析文件、文件流及文件包条目。              |
| 查询提供       | `lookupProvide(ProvideLookupInfo info)`                                                      | 通过统一的 Provide 查询链路访问外部或辅助数据。 |

分析器可以读取当前任务中已经存在的分析结果。
由于分析器按照 `index` 升序执行，后续分析器可以使用前序分析器写入的结果构建分阶段分析链路。

通过上下文下载文件流或图片流时，如果返回对象包含输入流，调用方有义务关闭该输入流。

### AnalyserMaker

`AnalyserMaker` 根据分析器类型和参数构造分析器，主要方法如下：

| 方法签名                                                                    | 说明                         |
|-----------------------------------------------------------------------------|------------------------------|
| `boolean supportType(String type)`                                          | 判断是否支持指定分析器类型。 |
| `Analyser makeAnalyser(String type, String param) throws AnalyserException` | 根据类型和参数构造分析器。   |

系统依次检查当前 Spring 容器中的制造器，并使用第一个支持指定类型的制造器。
制造器应完成参数解析、参数校验以及脚本编译等构造阶段操作。

### AnalyserSupporter

`AnalyserSupporter` 用于描述一个分析器类型，主要方法如下：

| 方法签名                       | 说明                 |
|--------------------------------|----------------------|
| `String provideType()`         | 提供分析器类型标识。 |
| `String provideLabel()`        | 提供显示名称。       |
| `String provideDescription()`  | 提供类型说明。       |
| `String provideExampleParam()` | 提供示例参数。       |

SDK 中的 `AbstractAnalyserRegistry` 同时实现 `AnalyserMaker` 和 `AnalyserSupporter`，适合用于注册一个固定类型的分析器。

## 分析器的生命周期

### 构造

系统首次获取指定部件的作业本地缓存时，读取该部件下全部已启用的 `AnalyserInfo`，并按照 `index` 升序排列。

对于每条分析器信息，系统使用 `type` 查找支持该类型的 `AnalyserMaker`，
再将 `type` 和 `param` 传递给制造器构造 `Analyser`。

构造完成的分析器以 `AnalyserInfo.key` 为键保存到作业本地缓存。
参数解析、脚本编译和不可变规则构造通常应在此阶段完成，避免每次任务执行时重复处理。

作业本地缓存构造过程中，如果任意分析器构造失败，整个部件的缓存获取失败，任务无法进入正常分析阶段。

### 创建执行器

任务进入分析阶段后，系统按照作业本地缓存中的分析器信息主键列表依次处理分析器。

系统从实例映射中取得 `Analyser`，调用 `newExecutor()` 创建新的执行器。
同一个缓存中的分析器可以为多个任务分别创建执行器。

执行器应保存本次执行所需的临时状态，不应假设同一个执行器会被重复用于其它任务。

### 初始化

系统为当前分析器创建 `Context`，并绑定以下信息：

| 信息              | 说明                           |
|-------------------|--------------------------------|
| `sectionKey`      | 当前任务对应的部件主键。       |
| `analyserInfoKey` | 当前正在执行的分析器信息主键。 |
| `taskKey`         | 当前任务主键。                 |

随后，系统调用执行器的 `init(Context)` 方法。
SDK 的 `AbstractExecutor` 会保存该上下文，供 `analyse()` 使用。

`init(Context)` 不声明受检异常，通常只用于设置上下文。
复杂参数校验和可能失败的运行期准备工作可以在分析器构造阶段或 `analyse()` 开始时完成。

### 执行分析

初始化完成后，系统调用执行器的 `analyse()` 方法。

分析器可以通过上下文读取已有分析结果、维护分析器变量、执行 Provide 查询、更新任务信息，
并将分析结果或中间结果写入当前任务。

前一个分析器执行完成后，系统才会创建并执行下一个分析器的执行器。
当前实现不会并行执行同一个部件中的多个分析器。

所有分析器执行完成后，系统记录分析完成事件和耗时，并继续进入判断阶段。

`Analyser` 和 `Executor` 接口没有显式的销毁回调。
清除作业本地缓存后，系统不再持有其中的分析器实例，但不会主动调用分析器的资源关闭方法。
需要长期持有外部资源的自定义实现应谨慎设计资源生命周期，避免依赖不存在的销毁回调。

## 工作机制

### 作业本地缓存

作业本地缓存以 `Section.key` 为键，保存部件以及该部件的分析器、判断器和可视化器信息与实例。

分析器相关内容包括：

| 内容               | 说明                                             |
|--------------------|--------------------------------------------------|
| 分析器信息主键列表 | 保存执行顺序，按 `AnalyserInfo.index` 升序排列。 |
| 分析器信息映射     | 以 `AnalyserInfo.key` 为键保存配置信息。         |
| 分析器实例映射     | 以 `AnalyserInfo.key` 为键保存 `Analyser`。      |

缓存未命中时，系统读取部件及其已启用的分析器信息并构造分析器；缓存命中时直接复用已有实例。

修改 `AnalyserInfo.type`、`param`、`index` 或 `enabled` 后，已经存在的作业本地缓存不会自动重建。
需要清除作业本地缓存，使后续任务重新读取配置并构造执行链。

### 执行顺序

分析器信息通过 `child_for_section_enabled_index_asc` 预设查询，
只选择指定部件下已启用的记录，并按照 `index` 升序排列。

任务分析阶段按照该列表串行执行分析器。 如果多个分析器的 `index` 相同，不应依赖这些记录之间的固定先后顺序；需要确定依赖关系时，应配置不同的索引值。

后序分析器可以读取前序分析器写入的 `Analysis`，因此索引顺序也是分析结果依赖顺序。
调整索引可能改变分析结果，配置变更后应同时清除作业本地缓存。

### 分析结果与变量

`Analysis` 归属于任务，用于保存本次任务产生的分析结果。
分析器可以插入、更新或删除简单值、图片、图片包、文件和文件包等类型的分析结果。

`AnalyserVariable` 归属于分析器信息，用于保存跨任务状态。
变量的读取和修改不会自动绑定当前任务，分析器应使用当前
`AnalyserInfo.key` 维护自身变量，避免访问其它分析器的状态。

分析器上下文不会为多个操作提供整体事务语义。
如果执行器先写入若干结果，随后发生异常，已经完成的操作是否保留取决于对应操作处理器的事务边界。
自定义分析器不应假设整个 `analyse()` 方法失败后所有副作用都会自动回滚。

### 异常处理

分析器机制使用统一异常类型隔离构造和执行阶段的差异：

| 异常                               | 说明                                     |
|------------------------------------|------------------------------------------|
| `UnsupportedAnalyserTypeException` | 没有制造器支持指定的分析器类型。         |
| `AnalyserMakeException`            | 分析器参数解析、脚本编译或实例构造失败。 |
| `AnalyserException`                | 创建分析器或执行器过程中发生的通用异常。 |
| `AnalyserExecutionException`       | 分析器执行时发生参数、数据或转换异常。   |

执行器的 `analyse()` 可以抛出任意异常。
分析阶段中的任意分析器执行失败时，系统停止执行后续分析器，不再进入判断、可视化和下沉阶段。

系统会记录警告日志，创建作业失败事件，并将任务状态置为失败。
任务事件只包含通用失败提示，详细异常原因需要通过系统日志排查。

## 运维与配置

分析器扩展通过 `opt/opt-analyser.xml` 加载。
发行包中的默认文件预留了预设分析器的组件扫描配置，但默认均被注释。

启用对应分析器时，取消相应 `context:component-scan` 的注释，并重启节点使 Spring 重新加载组件。
具体配置方式请参阅 [Opt Directory](./OptDirectory.md)。

Telqos 中与分析器相关的常用命令如下：

| 命令                       | 说明                                                                   |
|----------------------------|------------------------------------------------------------------------|
| `jlc -l <section-id>`      | 查看指定部件的作业本地缓存，包括分析器信息、执行顺序和分析器实例。     |
| `jlc -c`                   | 清除全部作业本地缓存，使后续任务重新读取分析器、判断器和可视化器配置。 |
| `support --reset-analyser` | 根据当前加载的分析器注册器重置 `AnalyserSupport`。                     |

`support --reset-analyser` 只重置支持信息，不会清除作业本地缓存，也不会重新构造已经缓存的分析器。

排查分析器配置问题时，可以分别确认：

1. `opt-analyser.xml` 是否加载了对应实现包。
2. `AnalyserSupport` 中是否存在对应类型。
3. `AnalyserInfo` 是否归属于正确部件，且已启用。
4. `AnalyserInfo.type` 和 `param` 是否符合具体实现约定。
5. `jlc -l` 是否可以成功构造并显示分析器实例。
6. 配置变更后是否执行了 `jlc -c`。
7. 分析器依赖的前序分析结果、分析器变量和 Provide 查询数据是否存在且类型正确。

分析器实例可能被多个任务并发复用。 对于耗时较长的分析逻辑，应关注任务执行线程占用、外部查询耗时、结果大小以及脚本实现的线程安全性。
